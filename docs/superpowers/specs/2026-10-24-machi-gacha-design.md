# 旅ガチャ — 設計仕様書

- 作成日：2026-10-24
- プロジェクト：`tabi-gacha`
- アプリ名：**旅ガチャ**（タイトル画面に表示する）

---

## 1. 目的と背景

内輪のハッカソン（テーマ「地域活性・観光」）のために作る新規Webアプリ。

評価基準はゆるく、**作り手自身が面白いと思えるもの**を優先する。実用性の説得力よりも、一発で伝わる面白さを取る。ただし題材は架空ではなく**実在の日本の市町村**を扱う。

開発予算は **1人 × 3日（3人日）**、AIコーディング前提。この予算で作れるのは「コア体験ひとつ＋見せ場ひとつ」であり、ログイン・管理画面・投稿のモデレーション・サーバーサイドの作り込みはスコープに含めない。

## 2. コンセプト

> **無名な町ほどレアに出るガチャ。引いた町には、その町でしか成立しないミッションが付いてくる。**

ガチャを引くと実在の市町村が1つ出る。レア度は**町の無名さ（人口の少なさ）に反比例**する。つまり過疎であることが、このアプリの中では価値になる。「地域活性」への主張を、説明文ではなく**排出確率そのもの**に埋め込む。

引いた町には3枚のミッションと「行き方のコツ」が付き、実際に旅の口実として使える。達成するとポイントが入り、称号が上がる。引いた町はカードとしてコレクションに残り、その旅で撮った写真を貼れる。

## 3. 前提と制約

| 項目 | 内容 |
|---|---|
| 開発者 | 1人 |
| 期間 | 3日（3人日） |
| 手段 | AIコーディング |
| 利用端末 | スマホ優先（旅先で使う）。PCでも閲覧できるようモバイル幅を中央配置 |
| 認証 | なし |
| サーバー | なし（完全な静的サイト） |
| データ保存 | 端末内のみ（localStorage / IndexedDB） |
| ランニングコスト | ゼロ |

## 4. ガチャとレア度

### 4.1 出題プールから大都市を外す

レア度を「無名さ」に置くと矛盾が生じる。レアを低確率にすれば**大半の利用者が有名都市を引き、「知らない町に行かせる」という目的が壊れる**。逆にレアを高確率にすればガチャとして成立しない。

解決として、**出題プールを人口10万人未満の市町村に限定する**。これにより「何を引いても知らない町」が保証された上で、その内部にレア度の勾配を作れる。

### 4.2 レア度の定義と排出率

| レア度 | 人口 | 排出率 | 性格 |
|---|---|---|---|
| SSR | 3,000人未満 | 8% | 離島・山村。たどり着くこと自体が旅になる |
| SR | 3,000〜10,000人未満 | 22% | 小さな町。日帰りは厳しい |
| R | 10,000〜30,000人未満 | 35% | 中規模の町 |
| N | 30,000〜100,000人未満 | 35% | それでも多くの人は知らない |

**Nでも十分に無名**であることがこの表の要であり、「ハズレ」が存在しない設計になっている。レア度は人口から機械的に決まるため、人の判断は介在しない。

### 4.3 抽選アルゴリズム

町から直接抽選すると、該当する町の件数が多いレア度ばかりが出てしまう。そのため**二段階**で引く。

1. 上表の重みでレア度を決める
2. そのレア度に属する町から一様に1つ選ぶ

これにより件数の偏りと排出率が切り離され、データがどう偏っても排出率は設計どおりに保たれる。

### 4.4 モード

- **全国モード**：プール全体から抽選
- **地方モード**：選択した地方に属する町だけを候補にする。地方区分は `北海道 / 東北 / 関東 / 中部 / 近畿 / 中国 / 四国 / 九州沖縄` の8つ

地方は**利用者が一覧から自分で選ぶ**（現在地から自動で固定しない）。抽選ロジックは両モードで共通。地方モードで該当レア度の候補が空になった場合は、別のレア度で再抽選する。

### 4.5 回数制限

**1日1回・引き直し不可**。localStorageに最後に引いた日を持つだけで実装する。「出たら逃げられない」という制約がガチャの情緒を支える。

> **ハッカソンとの相性についての注記**：1日1回では3日間で3回しか引けず、コレクションもランクも空のまま発表を迎えることになる。これは「12. デモモード」で解決する。

### 4.6 アプリ内の注釈

出題プールを人口10万人未満に限定していることは、**アプリ内に明記する**。黙っていると「有名な観光地が出ない、品揃えの悪いガチャ」に見えてしまい、設計の意図が逆に伝わるため。

**常時表示（ホーム画面・ガチャボタンの下に1行）**

> 有名な街は入っていません ― 出るのは人口10万人未満の市町村だけ

**タップで展開する詳細**

> 旅ガチャには、人口10万人未満の市町村だけが入っています。知名度の高い街をあらかじめ外すことで、何を引いても「行ったことのない町」になるようにしました。
>
> そして、人口が少ない町ほどレアに出ます。このガチャでは**無名であることが価値**です。

展開した中にレア度表（4.2）も並べ、SSRが人口3,000人未満であることを見せる。

一行目を常時表示にするのは、**発表の場でこの注釈がそのまま主張の説明になる**ため。審査員に口で説明する前に、画面に出ている状態にしておく。

## 5. ミッション

### 5.1 構成：1枚引くとミッションが3枚

| 枠 | 内容 | 生成方法 |
|---|---|---|
| 1枚目 | **その町の固有ミッション** | 事前生成。町ごとに1つ固定 |
| 2〜3枚目 | **汎用ミッション**（どの町でも成立するもの） | 汎用プールからランダム抽選 |

固有ミッションを**固定枠**にするのが重要である。3枚すべてを同じプールから抽選すると、プールが大きいほど固有ミッションが出なくなり、最も価値のある部分が埋もれる。固有は必ず1枚付け、汎用だけを抽選することで「毎回違う」と「その町ならでは」が両立する。

### 5.2 汎用ミッションの成立条件

「どこでも適用できる」ミッションは、実際には存在しない。「漁港で朝市をのぞく」は内陸で成立せず、「温泉で一服」は温泉のない町で破綻する。**1枚でも成立しないミッションが出ると、作り込みの甘さが一撃で伝わる。**

対策として、

- 町データに**タグ**を持たせる（`海沿い` / `山間` / `温泉あり` / `鉄道駅なし` など）
- 汎用ミッション側に**成立条件**（必要なタグ）を書く
- 抽選時に条件を満たすものだけを候補にする

実装は配列のフィルタで済む。副産物として、汎用ミッションでありながらその町に合って見える効果が得られる。

条件を満たす汎用ミッションが2つ未満になった場合は、**成立条件を持たないミッション**で補う。そのためプールには条件なしのミッションを常に数個含めておく。

汎用プールは30〜50個。AIに案を出させ、人が選別して確定する（生成コストはほぼゼロ）。

### 5.3 達成の扱い

**自己申告**とする。チェックボックスを押せばポイントが入る。GPSによる到達判定やAIによる写真判定は**行わない**。

理由：判定精度の問題で「達成したのに認められない」が起きると体験が致命的に壊れる。一方で自己申告の弱点（嘘をつける）は、一人用のアプリであるため実害がない。写真は達成の証明ではなく、思い出として任意で添えるものとする。

達成に期限は設けない。引いたカードはいつ達成しても構わない。

## 6. 行き方

### 6.1 役割分担：事実はGoogleマップに、コツはAIに

日本の公共交通の経路検索をAPIで正確に出すのは難しい領域であり、3人日で踏み込むべきではない。そのため役割を分ける。

- **正確な経路 → Googleマップに委譲**。出発地と町の座標からURLを組み立て、「Googleマップで経路を開く」ボタンを置く。**APIキー不要・無料・利用制限なし**
- **定性的なコツ → AIが事前生成**。「最寄り駅はどこか」「駅から先の交通手段」「バスの本数が少ない」「冬季の積雪」といった注意点

本数や時刻のような具体の数値はAIが誤りやすいため、断定を避ける文体で生成させる。

### 6.2 事前生成の制約：出発地に依存しない内容に限る

事前生成する「行き方のコツ」は、**出発地に依存しない内容に限定しなければならない**。「東京から3時間」と書くと大阪の利用者には嘘になる。

したがって事前生成するのは、その町に固定の情報（最寄り駅、駅からのアクセス手段、現地の交通事情、季節の注意）のみ。出発地に依存する所要時間と経路はGoogleマップのリンクに委譲する。

### 6.3 出発地の取得

ブラウザのGeolocationで**現在地を取得**する。現在地の用途は**経路の出発地のみ**であり、出題範囲の絞り込みには使わない（絞り込みは地方モードの手動選択で足りる）。

取得を拒否された場合・失敗した場合は、**駅名または市区町村の手入力**にフォールバックする。現在地がなくてもガチャは引ける。

Geolocationの利用にはHTTPSが必要なため、デプロイ先はHTTPSが付く環境とする。PCでの現在地はIP推定で精度が低いため、手入力の経路は常に用意しておく。

### 6.4 現在地についてのアプリ内注釈

**ブラウザの位置情報ダイアログを出す前に、自前の説明を表示する。** 一度拒否されると再許可の手順が分かりにくく、無言で許可を求めると拒否される確率が上がるため。

> **現在地を使わせてもらえますか**
>
> 行き方を調べるときの「出発地」として使います。このアプリにサーバーはないので、現在地がどこかに保存されることはありません。経路を開く操作をしたときだけ、出発地としてGoogleマップに渡されます。
>
> 許可しなくてもガチャは引けます（出発地を手で入力できます）。

**文面の正確さについて**：「端末の外に一切出ない」と書いてはならない。経路を開く際にGoogleマップのURLへ出発地として含まれるため、それは事実に反する。アプリ自身は保存も送信もしない、渡るのはGoogleマップを開いたときだけ、という切り分けを明示する。

同じ趣旨の説明をプロフィール画面にも常設し、あとから確認できるようにする。

## 7. ポイントとランク

### 7.1 ポイント

**獲得ポイント ＝ 町のレア度 × 達成したミッション数**

| レア度 | 1枚あたり | 3枚達成時 |
|---|---|---|
| SSR | 100 | 300 |
| SR | 50 | 150 |
| R | 25 | 75 |
| N | 10 | 30 |

### 7.2 ランク（称号）

累計ポイントで称号が変わる。閾値テーブルと比較処理のみで実装する。

| 累計ポイント | 称号 |
|---|---|
| 0 | 旅の見習い |
| 100 | 寄り道の人 |
| 500 | 旅人 |
| 1,500 | 辺境の開拓者 |
| 5,000 | 日本を踏み尽くす者 |

ポイントの用途はランクのみ。引き直し券やモード解放には使わない。

## 8. コレクションと写真

引いた町は**カード**としてコレクションに残る。カードを選ぶと詳細が開き、**その旅で撮った写真が一覧で並ぶ**。

写真はカードに属する（1枚のカードに複数の写真）。この親子関係はそのままテーブルの形になるため、将来のDB移行と素直に噛み合う。

写真は端末のIndexedDBにBlobとして保存する。代償は3つあり、受け入れる：**端末を変えると消える / 他人に見せられない / ブラウザのデータを消すと失われる**。

### 8.1 データ保存についてのアプリ内注釈

この代償は**アプリ内に明記する**。黙っていると、ブラウザのデータを消した利用者がカードと写真をまとめて失い、事故になる。

**プロフィール画面に常設**

> カードと写真は、この端末の中にだけ保存されます。ブラウザのデータを消すとすべて失われ、別の端末に引き継ぐこともできません。

**初めて写真を追加するときに1回だけ表示**

> 写真はこの端末の中にだけ保存されます。大切な写真は端末のカメラロールにも残しておいてください。

写真は失ったときの痛みが最も大きいため、追加する直前という最も伝わる場所で一度だけ警告する。毎回出すと邪魔になるので、初回のみとする。

│  旅ガチャ                      │
│  モード選択：全国 / 地方▾      │
│  ［ 引 く ］                   │
│  今日はあと0回  ランク：旅人    │

│  有名な街は入っていません ―    │   ← 4.6 の注釈。常時表示
│  出るのは人口10万人未満の      │      タップでレア度表まで展開
│  市町村だけ               ▾   │

            │ 演出
            ▼

│  ─────────────────  │
│  ミッション                   │
│  □ 固有：△△神社の…          │
│  □ 汎用：地元の人に…         │
│  □ 汎用：名前を知らない…      │
│  ─────────────────  │
│  行き方のコツ（AI）           │

**カード詳細をガチャ結果と共用する**のが工数の要である。同じものを2回作らないため画面が実質1つ減る。引いた瞬間にコレクションへ自動保存されるので「保存する」操作も不要。

## 10. データモデル

永続化は**1つのモジュールに閉じる**。画面側は `localStorage` や `indexedDB` を直接触らず、「保存する／取り出す」という操作だけを呼ぶ。データの形は**最初からテーブルとして設計**し、`id` と作成日時、外部キー相当のフィールドを持たせる。

| 名前 | 置き場所 | フィールド |
|---|---|---|
| `towns` | 静的JSON（読み取り専用） | `id`, 町名, 都道府県, 地方, 人口, レア度, 緯度, 経度, タグ[], 固有ミッション, 行き方のコツ |
| `generic_missions` | 静的JSON（読み取り専用） | `id`, 文面, 成立条件（必要タグ）[], 難易度 |
| `pulls` | 端末（localStorage） | `id`, **`member_id`**, `town_id`, 引いた日時, 固有ミッションの達成状況, 抽選された汎用ミッション2件（`generic_mission_id` と達成状況）, 獲得ポイント |
| `photos` | 端末（IndexedDB） | `id`, `pull_id`, 画像Blob, 撮影日時 |
| `profile` | 端末（localStorage） | **`member_id`**, 累計ポイント, ランク, 最後に引いた日, スキーマバージョン |

固有ミッションは `town_id` から引けるため `pulls` に文面を持たせず、達成状況だけを記録する。汎用ミッションは抽選結果なので、どれが出たかを `pulls` に残す必要がある。

### 10.1 `member_id` — 将来のログイン・DB移行のために

`profile` に **`member_id`**（初回起動時に端末で生成するUUID）を持たせ、`pulls` から参照する。現在は1端末1人しか存在しないため実行時には何の役にも立たないが、**将来ログインとDBを足すときの受け皿**として最初から入れておく。

これにより、テーブルの形が将来の姿と同じになる：

```
members (id, 累計ポイント, ランク, 最後に引いた日)   ← 現在の profile
  └─ pulls (id, member_id, town_id, ...)
       └─ photos (id, pull_id, ...)
```

`photos` は `pull_id` から `member_id` を辿れるため、`member_id` を持たせない（非正規化しない）。

**ログインを足すときの扱い**：端末で生成した `member_id` を、そのままサーバー側のアカウントIDにはしない。両者は別物として扱い、`member_id` は「**この端末に溜まったデータを、このアカウントに引き継ぐ**」ための突き合わせキーとして使う。端末のUUIDをアカウントIDに昇格させると、同一人物が複数端末を使った場合に破綻する。

## 11. データ源と事前生成

### 11.1 事実と創作の切り分け

**LLMには事実を作らせない。** これが品質の分かれ目である。

- **実データから取る（LLMを通さない）**：市町村名、自治体コード、人口（総務省の住民基本台帳人口、またはe-Statの国勢調査CSV）、緯度経度（国土数値情報／国土地理院）。レア度はこの人口から機械的に決まる
- **LLMに作らせる（事前生成）**：固有ミッションの文面、行き方のコツ、タグ

### 11.2 生成の手順

LLMへの呼び出しは**APIを使わない**。契約済みの Claude Pro プランに含まれる **Claude Code のセッション内で生成する**ため、追加費用はかからない。Anthropic SDK もAPIキーも使わない。

1. **骨格を機械生成する** — 実データから `towns.json` の骨格（町名・自治体コード・人口・緯度経度・レア度・地方）を作る。ここはLLMを通さず、CSVの変換スクリプトで処理する
2. **分割して埋める** — 骨格を30〜50件ずつに分け、Claude Code に渡して固有ミッション・行き方のコツ・タグを埋めさせる
3. **機械チェックする** — 検証スクリプトにかける
4. **目視で直す** — 不自然な記述を手で修正する

APIを使わない代償は2つあり、それぞれ対策を置く。

**代償1：構造化出力でスキーマを固定できない。**
→ **検証スクリプト `scripts/validate-towns.ts` を用意する。** 必須フィールドの欠落、タグが既定の語彙に収まっているか、文面の文字数上限、固有ミッションにその町固有の語が含まれているか、などを機械的に弾く。Vitestから実行できるようにし、**データが壊れたらテストが落ちる**状態にしておく。スキーマの保証を「生成時」から「生成後の検証」に移すということであり、この検証スクリプトは省略できない

**代償2：再現性が落ちる（コマンド1発で作り直せない）。**
→ 生成に使った指示文を `scripts/prompts/` にファイルとして残す。追加生成や作り直しのときに同じ基準で生成できるようにする

### 11.3 第1弾の対象件数

人口10万人未満の市町村は1,000件を超える見込みだが、30〜50件ずつの分割実行で埋めるため、全件を仕上げるには回数がかかる。費用はかからないが、時間がかかる。

**第1弾は300件程度にキュレートする。** 余裕があれば拡張する。

拡張を安全にするため、**骨格は全件分を機械生成しておき、ミッションが埋まっている町だけを出題プールに入れる**。町データに生成済みフラグを持たせ、未生成の町は抽選対象から外す。これにより、あとから何件追加しても既存の動作が壊れない。

キュレーションは**地方ごと・レア度ごとに均等に抽出する**。地方モードで候補が少ないと同じ町ばかり出てしまうため、8地方それぞれに全レア度の町が十分な数だけ存在する状態を保つ。

### 11.4 事前生成を選ぶ理由

| | 事前生成（採用） | 実行時生成（不採用） |
|---|---|---|
| 実行時コスト | ゼロ | 引くたびに課金 |
| APIキー・課金 | **不要**（Claude Code で生成するため） | APIキーとサーバー側の処理が必須 |
| 外部依存 | なし | 当日APIが詰まると停止 |
| 品質確認 | **目で見て直せる** | 発表中に誤りが出ても手が出せない |
| 毎回違うか | 汎用ミッションの抽選で担保 | 完全に毎回違う |

ハルシネーションへの備えが、事前生成を選んだ最大の実利である。存在しない施設を挙げるような誤りは起こり得るが、生成物が静的JSONとして手元にあるため目視で修正できる。

### 11.5 写真素材

町の写真は**使わない**。権利処理が面倒であり、3人日の予算に対して見返りが小さい。どうしても使う場合はWikimedia Commons（CC）に限り、ライセンス表記を添える。

## 12. デモモード

プロフィール画面の奥に置く。

- **回数制限の解除**（1日1回を外す）
- **現在地の擬装**（任意の町にいる状態にする）
- **次に引くレア度の指定**

最大の理由は**回数制限**である。1日1回のままでは3日間で3回しか引けず、コレクションもランクも空のまま発表を迎えることになる。作り手自身が動作を確認できないという問題も同じ原因から生じる。

現在地の擬装は、会場から動かずに「別の出発地から見た行き方」を見せるためのもの。レア度の指定は、発表でSSRを確実に出すためのもの。

デモモードは**発表に実質必須**であり、発表では隠さず「デモモードです」と述べる前提とする。

## 13. 壊れ方の設計

| 状況 | 振る舞い |
|---|---|
| 現在地を拒否／取得失敗 | 駅名・市区町村の手入力に切り替える。ガチャ自体は現在地なしで引ける |
| IndexedDBが使えない（プライベートブラウズ等） | **写真機能だけを無効化し、他は通常動作**。アプリ全体を落とさない |
| 保存データのスキーマ変更・破損 | スキーマバージョンを持ち、読めない場合は初期化する。**黙って壊れず、初期化したことを画面に出す** |
| 抽選で候補が空 | 別のレア度で再抽選する |

## 14. テスト方針

3人日なので全面的なテストは張らない。**純粋なロジックだけをテストで固める。**

対象（すべて入力と出力だけの純関数にできる）：

- レア度の重み付き抽選
- 出題プールのフィルタ（人口上限、地方）
- 汎用ミッションの成立条件フィルタ
- ポイント計算
- ランク判定

これらはテストを先に書く形（TDD）で進める。UIと演出は手で触って確認する。テストランナーは Vitest。

## 15. 技術構成

| 項目 | 選択 |
|---|---|
| ビルド | Vite |
| UI | React + TypeScript |
| スタイル | Tailwind CSS |
| テスト | Vitest |
| データ整備・検証スクリプト | TypeScript（Anthropic SDK は使わない） |
| デプロイ | **Vercel**（無料枠、HTTPS付き） |

**完全なクライアントサイドアプリとして作る。** サーバー処理が一切ないため設定が最小で済み、端末内データを主役とするアプリと相性が良い。サーバーサイドレンダリングを挟む構成では「サーバーには端末のデータが見えない」ことに起因する表示のズレに時間を取られる。今回はこれを最初から回避する。

将来DBを足す場合も、ブラウザからDBを直接扱えるサービス（Supabase等）を使えばこの構成のまま移行できる。移行時に差し替えるのは永続化モジュールの中身だけで、書き直しにはならない。

## 16. スコープ外

明示的に作らないもの：

- ログイン・ユーザー認証
- サーバーサイドの処理、API、データベース
- 他の利用者との共有、ランキング、地図への集合的な蓄積
- GPSによる到達判定、AIによる写真判定
- 公共交通APIによる経路検索（Googleマップへのリンクで代替）
- 町の写真素材
- ポイントの用途の拡張（引き直し券、モード解放）
- 「カードの裏面を現地で開封する」仕組み（検討のうえ不採用）

## 17. 3日間の進め方

| | やること | 切り落とせるか |
|---|---|---|
| **1日目** | データ整備（骨格の機械生成 → Claude Code でミッション生成 → 検証スクリプト）→ 抽選ロジック（テスト付き）→ ガチャで町が出る | 不可 |
| **2日目** | カード詳細・ミッション・行き方・Googleマップ連携・永続化層・コレクション・ポイント／ランク | 不可 |
| **3日目午前** | 写真（IndexedDB） | **可。遅れたら最初に切る** |
| **3日目午後** | ガチャ演出・見た目の仕上げ・デモモード・デプロイ・発表準備 | 不可 |

**1日目の終わりに「町が出る」状態を作ることが最重要。** ここが動けば以降はすべて積み増しであり、どこで時間が尽きても発表できるものが手元に残る。

写真機能を最後の層に置くことで、時間が尽きたときに**切り落とすのが写真だけで済み、他は壊れない**。写真がなくてもアプリとして完結している状態を先に作る。
